# Review brief — gumroad#7682

`bin/branch-specs` maps a branch diff to the specs CI runs. `spec/bin/branch_specs_test.rb` is its
standalone self-test (throwaway git repos, no Rails); it runs on every PR in the `migration_versions`
job. Read both files at HEAD.

## What this diff does

Adds three paths to `ESCALATE_PATTERNS`:

- `app/javascript/components/DownloadPage/Layout.tsx`
- `app/javascript/components/DownloadPage/WithContent.tsx`
- `app/javascript/pages/UrlRedirects/Read.tsx`

and rewrites their three self-test pins to include the co-located `.test.tsx` that exists in the repo,
plus one new pin asserting the co-located-vitest shortcut still applies to an unmapped leaf module.

## The defect being fixed

#7654 excluded `Layout.tsx` / `WithContent.tsx` from the `DownloadPage/` directory rule via a negative
lookahead, so they map to nothing and escalate through the mapping-gap rule (`bin/branch-specs:554`).
That rule runs AFTER the co-located-vitest shortcut at `bin/branch-specs:509-523`, which treats
"mapped to nothing" as "covered by vitest" when a `.test.tsx` sits beside the source. so once such a
file exists, a source-only change exits 0 with an empty list and `tests.yml` runs
`spec/models/user_spec.rb` as the floor instead of the full suite.

`Read.tsx` is the same shape and its checked-in pin already asserted escalation, but the pin's fixture
omitted `Read.test.tsx` (which exists in the repo, added in #7366), so it passed vacuously.

2. Does anything else depend on those three paths NOT escalating — e.g. another mapping, a documented
   lane cost, or a pin that now contradicts?
3. Is the new "leaf module still rides the shortcut" pin load-bearing, or does it pass for an unrelated

5. Is `Read.tsx` genuinely a file that must run the full suite, or should its co-located vitest plus
