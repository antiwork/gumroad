bin/test-confidence — Vitest support. Verified behaviour, before vs after.

All transcripts below are real runs of bin/test-confidence in this repo, with a
cached plan fixture pinning which test the gate selects. Fixtures were reverted
after each run; `git status` showed only bin/test-confidence and this file.


1. THE ORIGINAL BUG — planner picks a Vitest test, gate dies having run nothing
------------------------------------------------------------------------------
Diff: 4 files, a UI-only change to two React inputs whose only coverage is
colocated Vitest tests.

BEFORE (main)
    TEST CONFIDENCE
  EXIT=1          <- died at the banner on `grep "spec/"`, 0 tests run

AFTER
   80%   app/javascript/.../CustomReceiptTextInput.test.tsx          1/1
   95%   app/javascript/.../CustomViewContentButtonTextInput.test.tsx 1/1
   99%   spec/requests/products/edit/receipt_spec.rb   confirmed pre-existing
  99% confidence — 2 tests passed in 122s.  Safe to commit.
  EXIT=0


2. A FAILING FRONT-END TEST MUST BE REPLAYED, NOT GUESSED AT
------------------------------------------------------------
The old verdict came from comparing basenames, which cannot see a test broken by
a differently-named dependency. Fixture: wrap Input.tsx's <input> in an extra
<div>; leave InputGroup.test.tsx (which imports it) untouched.

  HEAD tally: Tests  2 failed | 1 passed (3)
  VERDICT: regression (kind=replayed) -> gate HALTS, EXIT=1   (correct)

Control — a genuinely pre-existing failure must still be skipped, or a gate that
halts on everything is useless. Search.test.tsx, already red on merge-base
(3 failed | 10 passed), branch touches an unrelated file:

  VERDICT: confirmed pre-existing -> skipped, EXIT=0


3. A NONZERO REPLAY IS NOT EVIDENCE UNLESS TESTS ACTUALLY RAN
--------------------------------------------------------------
Vitest exits nonzero in three shapes and only the first says anything about the
test:

  1. executed, some failed   "Tests  1 failed | 1 passed (2)"
  2. collected nothing       "Tests  no tests"
  3. never started           no "Tests" line at all (e.g. broken config)

Fixture: merge-base has a broken vitest.config.ts (Vitest cannot start) and a
test that would pass; the branch repairs the config and breaks a shared dep, so
the test genuinely regresses.

  BEFORE  rc=0 confirmed pre-existing -> "Safe to commit"  ** regression shipped **
  AFTER   rc=1 regression (kind=unreplayable) -> gate HALTS

vitest_executed_tests() now requires a real per-test tally. Checked against all
eight captured output shapes (real failure / all passing / skipped-only = ran;
collection error / startup error / no test files / empty / the word "tests" in
prose = did not run).

Trap worth recording: Vitest colours its summary even through a pipe, so the
tally arrives as $'\033[2m      Tests\033[22m ...'. The first version anchored on
'^[[:space:]]*Tests' and silently never matched. ANSI is stripped before matching.


4. AN UNAVAILABLE REPLAY IS NOT EVIDENCE EITHER
------------------------------------------------
Same shared-dependency regression as (2), but the replay is made unavailable the
way a real branch would — touch package.json, the documented bail-out.

  BEFORE  "likely pre-existing (unverified)" -> Safe to commit, EXIT=0
  AFTER   FAILED (could not verify against merge-base), EXIT=1
          Reason: package.json/package-lock.json changed on this branch, so this
          checkout's node_modules is not the dependency set merge-base would install

There is no cheap substitute for the replay, so the basename fallback is deleted
rather than improved (`is_likely_preexisting` is gone; it had no other caller).
Each inconclusive path now names its reason: manifests changed / no node_modules
to lend / worktree or symlink failed / Vitest executed no tests on either side.


5. BRANCH PATCHES CONTAMINATE THE BORROWED node_modules
--------------------------------------------------------
postinstall runs `patch-package`, so a file under patches/ rewrites an installed
dependency with neither manifest changing. Fixture: edit the installed copy of
class-variance-authority so cva() returns "", add the patch file, leave both
manifests untouched.

  BEFORE  "confirmed pre-existing" -> Safe to commit, EXIT=0
          (worst case: the replay really ran — against the branch's own
          contaminated tree)
  AFTER   FAILED (could not verify against merge-base), EXIT=1
          Reason: install-time inputs changed on this branch
          (patches/class-variance-authority+0.7.1.patch)

The drift guard now covers package.json, package-lock.json, npm-shrinkwrap.json,
yarn.lock, pnpm-lock.yaml, .npmrc, patches/**, and any nested */package.json.
Untracked files count too — a newly added patch is invisible to `git diff` but
already installed, which is exactly when the tree is contaminated.

Known limit: a node_modules hand-edited by something other than a tracked
install-time input is undetectable from git. Not reachable through a branch,
which is what this gate judges. Verified the guard does not latch: with the same
contaminated dependency but the patch file deleted, the gate goes back to
trusting the replay (EXIT=0).


6. A MILESTONE MUST NOT CLAIM CONFIDENCE IT DIDN'T EARN
--------------------------------------------------------
A plan can name a stale or non-test path. Two problems: the discard was silent,
and the milestone still advanced its confidence with zero tests behind it.

  99% names only app/javascript/.../DeletedLongAgo.test.tsx (does not exist)

  BEFORE  EXIT=1, dying at the banner — a second instance of the same
          `set -e` + non-matching-grep bug this PR set out to fix
  AFTER   ⚠ discarded (not a runnable test file): .../DeletedLongAgo.test.tsx
          ⚠ 99% not claimed — no runnable test in this milestone's plan;
            confidence stays at 80%
          EXIT=1, because the gate never reached its bar

Control — a milestone whose tests all ran in an EARLIER milestone must still
advance (the SEEN_RUN dedupe), which is why the guard keys on planned-runnable
rather than on the post-dedupe count:

  80%: InputGroup.test.tsx    99%: InputGroup.test.tsx (identical)
  ✅ 80% — 1 test — 3s, no spurious warning, EXIT=0

  And with a genuinely new test at 99%: 99% confidence — 2 tests passed, EXIT=0.
